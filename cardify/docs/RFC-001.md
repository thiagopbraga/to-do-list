# RFC-001 — Arquitetura do Gerador de Flashcards com IA

**Autor:** —
**Status:** Proposta (aberta para comentários)
**Versão:** 1.1 — backend em NestJS
**Data:** 21/07/2026
**Documento de origem:** PRD — Gerador de Flashcards com IA v1.0
**Revisores sugeridos:** backend, infra, produto

> **Mudanças da v1.0 → v1.1.** O backend passa de Python/FastAPI para NestJS. Isso afeta ingestão (§3), validação (§4), **empacotamento `.apkg` (§5, reescrito)**, fila (§7) e testes (§9). O PRD recomendava Python justamente por causa do `genanki` e do `PyMuPDF`; esta revisão explica o que substitui cada um e o que se perde no caminho.

---

## 1. Contexto

O PRD define um produto que recebe material de estudo (PDF, texto, YouTube) e devolve um baralho `.apkg` importável no Anki. Esta RFC descreve como construir isso em Node/TypeScript.

O critério de aceite nº 4 do PRD — *"exportar um `.apkg` que importa no Anki desktop e no AnkiDroid sem erro e sem duplicata"* — é o requisito que mais restringe o desenho técnico. Com backend em Node ele fica **mais caro**, porque não existe equivalente maduro do `genanki` no ecossistema JavaScript. A §5 trata disso como o principal risco desta revisão.

### 1.1. Objetivos técnicos

- Processar um PDF de 300 páginas sem estourar contexto, memória ou orçamento.
- Gerar `.apkg` correto, incluindo cloze, com reimportação idempotente.
- Manter o custo de LLM abaixo de R$ 0,60 por baralho de 100 cards, com teto rígido por job.
- Entregar amostra de 10 cards em menos de 15s para usuário anônimo.

### 1.2. Não-objetivos

- Implementar o algoritmo de revisão espaçada (o Anki faz isso).
- Suportar mais de um idioma na v1.
- Alta disponibilidade multi-região.

## 2. Visão geral

```

                 └──────┬───────┘        └──────┬──────┘
                        │                       │
                 ┌──────▼───────┐        ┌──────▼──────────────┐
                 │  Object      │◄───────│  NestJS Worker      │
                 │  Storage     │        │  (sem HTTP)         │
                 └──────────────┘        └──────┬──────────────┘
                                                │
                        ┌───────────────────────┼──────────────────┐
                        ▼                       ▼                  ▼
                 ┌────────────┐         ┌────────────┐   ┌──────────────────┐
                 │ Ingestão   │         │ Geração    │   │ Empacotamento    │
                 │ pdfjs-dist │         │ LLM 2 est. │   │ better-sqlite3   │
                 │            │         │ + zod      │   │ + archiver       │
                 └────────────┘         └────────────┘   └──────────────────┘
```

**Monorepo, dois processos, um código.** `apps/api` (HTTP) e `apps/worker` (sem servidor HTTP), compartilhando `libs/` com entidades, serviços de domínio e clientes. O worker sobe com `NestFactory.createApplicationContext()` — mesmo container de injeção de dependências, sem custo de rede exposta.

O worker executa três estágios sequenciais dentro de um mesmo job, com checkpoint em banco entre cada um. Falha no estágio 3 não reexecuta os estágios 1 e 2 — que são os caros.

### 2.1. Stack

| Camada | Escolha | Nota |
|---|---|---|
| API | NestJS + Fastify adapter | Fastify pelo throughput e por upload melhor resolvido |
| Fila | **pg-boss** | Fila real sobre Postgres; substitui o `SKIP LOCKED` manual da v1.0 |
| ORM | **Drizzle** | SQL-first; `FOR UPDATE` e CTEs sem brigar com a abstração |
| Validação HTTP | `class-validator` + `ValidationPipe` | Padrão do Nest |
| Validação de LLM | **zod** | Substitui o Pydantic; schema único compartilhado com o front |
| PDF | **`pdfjs-dist`** | Substitui o PyMuPDF (§3.2) |
| `.apkg` | **`better-sqlite3` + `archiver`** | Substitui o `genanki` (§5) |
| OCR (v1.1) | `tesseract.js` | Mais lento que o Tesseract nativo; medir antes de prometer |

**Atenção de build:** `better-sqlite3` é módulo nativo. A imagem Docker precisa de toolchain de compilação (`python3`, `make`, `g++`) no estágio de build, ou binário pré-compilado compatível. Evitar Alpine — a incompatibilidade musl/glibc em módulos nativos custa horas. Usar `node:22-bookworm-slim`.

## 3. Pipeline de ingestão

### 3.1. Upload e validação

1. Cliente pede URL assinada de upload; envia direto para o object storage (não passa pela API).
2. Validação por **magic bytes**, não por extensão (`file-type`).
3. Limites rígidos: 50 MB, 300 páginas, 10 minutos de wall clock no parsing.
4. Calcular SHA-256 do arquivo em stream. Serve para cache e idempotência (§7).

**Segurança:** parsers de PDF são superfície de ataque conhecida. Em Node isso é mais delicado do que em Python, porque `worker_threads` compartilha o processo — não é isolamento de verdade. O parsing roda em **processo separado** (`child_process.fork` ou container próprio de worker), com `--max-old-space-size` limitado, sem credenciais de escrita no banco e com timeout duro imposto pelo pai. PDF malicioso derruba o filho, não o serviço.

### 3.2. Extração de texto — `pdfjs-dist` no lugar do PyMuPDF

O `page.get_text("dict")` do PyMuPDF entregava spans com tamanho de fonte e posição de graça. O equivalente em Node é `getTextContent()` do `pdfjs-dist`, que devolve itens assim:

```ts
type TextItem = {
  str: string;
  transform: number[];  // matriz 6 posições
  width: number;
  height: number;
  fontName: string;
};
```

O que precisamos está lá, só menos explícito:

- **Tamanho de fonte** ≈ `Math.hypot(transform[2], transform[3])` (escala vertical da matriz). Na prática `transform[3]` sozinho serve para a esmagadora maioria dos PDFs sem rotação; usar o `hypot` como forma segura.
- **Posição vertical** = `transform[5]`, com origem no canto inferior esquerdo. Normalizar contra `page.getViewport({scale:1}).height` antes de comparar entre páginas de tamanhos diferentes.
- **Negrito** é inferido pelo `fontName` (contém `Bold`/`Black`), não por atributo. Menos confiável que no PyMuPDF; usar só como sinal secundário.

**Perda real em relação ao PyMuPDF:** o pdf.js não agrupa itens em blocos ou linhas. Ele devolve fragmentos de texto soltos, às vezes quebrando uma palavra em dois itens. Precisamos de um passo de agrupamento próprio: ordenar por `y` decrescente e `x` crescente, juntar itens cuja diferença de `y` seja menor que meia altura de linha, e inserir espaço quando o gap horizontal exceder ~25% da largura média do glifo. São ~80 linhas de código que o PyMuPDF dava pronto. **Este é o custo concreto da mudança de stack no estágio de ingestão.**

*Alternativa avaliada:* o pacote `mupdf` (bindings WASM oficiais do MuPDF) dá paridade quase completa com o PyMuPDF, incluindo agrupamento em blocos via `StructuredText`. Vale reavaliar se o agrupamento manual do pdf.js se mostrar frágil nos fixtures reais. Ficou fora da recomendação principal por ser dependência WASM mais pesada e com menos uso em produção no ecossistema Node.

**Detecção de PDF escaneado:** se a razão `caracteres extraídos / número de páginas` for menor que ~80, tratar como escaneado. Na v1, recusar com mensagem clara. Na v1.1, rotear para `tesseract.js`.

### 3.3. Limpeza de cabeçalho e rodapé

Heurística, não regex fixa:

1. Agrupar linhas por posição vertical normalizada (faixas do topo e do rodapé, ~8% da altura).
2. Normalizar o texto (remover dígitos, minúsculas, sem acento).
3. Uma linha que aparece em mais de 60% das páginas, na mesma faixa vertical, é ruído estrutural — remover.
4. Numeração de página cai automaticamente nessa regra depois da normalização de dígitos.

Isso resolve marca d'água de cursinho e cabeçalho de aula, que são a principal fonte de card lixo.

### 3.4. Chunking semântico

Chunking por caractere quebra o raciocínio no meio e produz card sem contexto. Em vez disso:

1. Inferir hierarquia de títulos pela distribuição de tamanhos de fonte do documento (o tamanho modal é corpo de texto; tamanhos acima são títulos, ordenados por nível).
2. Quebrar nos títulos detectados.
3. Se um bloco exceder ~2.000 tokens, subdividir em parágrafos com sobreposição de ~120 tokens.
4. Se um bloco tiver menos de ~200 tokens, fundir com o vizinho.
5. Persistir cada chunk com sua trilha de títulos (`capítulo > seção > subseção`), que vira tag do card e contexto do prompt.

Contagem de tokens com `js-tiktoken` (porta pura em JS; a variante WASM `tiktoken` é mais rápida se o volume exigir).

Fallback quando não há estrutura de fonte detectável: quebra por parágrafo duplo com o mesmo alvo de tamanho.

## 4. Pipeline de geração

### 4.1. Dois estágios

**Estágio A — extração de fatos (modelo econômico).** Entrada: um chunk + trilha de títulos. Saída: lista de afirmações atômicas, cada uma marcada como `definicao | enumeracao | relacao | numero | processo`.

**Estágio B — formulação de cards (modelo melhor).** Entrada: lote de fatos + área de estudo + preferência de tipo. Saída: cards.

**Por que separar.** O estágio A consome mais tokens de entrada (o documento inteiro passa por ele) e é a tarefa mais mecânica. O estágio B processa volume muito menor e é onde a qualidade da redação importa. Usar o modelo caro só onde ele muda o resultado é o que sustenta o teto de custo do PRD.

*Alternativa rejeitada:* passe único com modelo forte. Mais simples, ~3x mais caro, sem ganho mensurável de qualidade.

### 4.2. Saída estruturada com zod

O zod substitui o Pydantic e ganha uma vantagem que o Pydantic não tinha: **o mesmo schema é importado pelo front**, então o tipo do card na tela de revisão e o tipo esperado do LLM não podem divergir.

```ts
export const CardSchema = z.object({
  tipo: z.enum(['basico', 'cloze']),
  frente: z.string().min(3).max(300),
  verso: z.string().min(1).max(500),
  textoCloze: z.string().nullable(),
  tagSecao: z.string(),
  fonteOffset: z.number().int().nonnegative(),
});

export const RespostaGeracaoSchema = z.object({ cards: z.array(CardSchema) });
export type Card = z.infer<typeof CardSchema>;
```

Em caso de JSON inválido: uma tentativa de reparo (reenvio só do trecho quebrado), depois descarte do chunk com log. Nunca falhar o job inteiro por causa de um chunk.

`fonteOffset` aponta para a posição no chunk original. Permite "ver de onde veio este card" e, mais importante, auditar alucinação.

### 4.3. Validação de cloze

Todo card cloze passa por validação antes de entrar no baralho. Cloze malformado é o defeito que mais gera reclamação, porque o erro só aparece dentro do Anki, depois da importação.

Regras aplicadas via `/\{\{c(\d+)::(.+?)(::.+?)?\}\}/g`:

- Ao menos uma oclusão presente.
- Índices começam em 1 e são contíguos (`c1`, `c2`... sem pular).
- Conteúdo ocluído não vazio e não idêntico à frase inteira.
- Chaves balanceadas.
- Texto fora das oclusões com pelo menos 15 caracteres — precisa sobrar contexto.

Card reprovado: uma tentativa de reformulação; se falhar de novo, converter para básico.

### 4.4. Deduplicação

Chunks com sobreposição geram cards quase idênticos. Sem embeddings no MVP:

1. Normalizar a frente (minúsculas, sem acento via `normalize('NFD')`, sem pontuação, sem stopwords).
2. Shingles de 3 tokens, similaridade de Jaccard.
3. Limiar 0,85 → manter o card com o verso mais curto (princípio da informação mínima).

### 4.5. Controle de custo por job

Cada job carrega um `orcamentoCentavos`. Antes de cada chamada, o custo estimado é debitado; ao passar do teto, o job encerra **com sucesso parcial** — entrega o que gerou, cobra cota proporcional e avisa o usuário.

Toda chamada de LLM é registrada em `llm_calls` (modelo, tokens in/out, custo, job, estágio). Sem esse ledger não há como saber se a margem do plano está de pé. Implementar como interceptor Nest no cliente de LLM, para que nenhuma chamada escape do registro por esquecimento.

## 5. Empacotamento `.apkg` — o ponto crítico desta revisão

Não existe equivalente maduro do `genanki` em Node. Esta seção é a que justifica ou derruba a escolha de stack.

### 5.1. Opções avaliadas

| Opção | Veredito |
|---|---|
| **A.** `anki-apkg-export` (npm) | **Rejeitada.** Sem manutenção há anos, note type fixo, sem cloze e sem GUID customizável. Falha exatamente nos dois requisitos duros da §5.3 e §5.4. |
| **B.** Sidecar Python só para empacotar | **Viável, não recomendada.** Mantém o `genanki` testado em produção, mas reintroduz um segundo runtime, um segundo deploy e um contrato de rede para uma única função. Se a opção C atrasar mais de uma semana, cair para cá sem cerimônia. |
| **C.** Empacotador próprio em Node | **Recomendada.** ~250 linhas sobre `better-sqlite3` + `archiver`, controle total sobre GUID, note type e cloze. |

### 5.2. O formato, sem mistério

Um `.apkg` é um zip contendo:

- `collection.anki2` — banco SQLite
- `media` — JSON de mapeamento; `{}` quando não há mídia
- arquivos de mídia nomeados `0`, `1`, `2`... (não usados na v1)

Tabelas que importam:

- **`col`** — linha única. Os campos `models`, `decks`, `dconf` e `conf` são JSON serializado.
- **`notes`** — `(id, guid, mid, mod, usn, tags, flds, sfld, csum, flags, data)`
  - `flds` = campos unidos pelo separador `\x1f`
  - `sfld` = primeiro campo, em texto puro (é o campo de ordenação)
  - `csum` = `parseInt(sha1(primeiroCampo).slice(0, 8), 16)` — o Anki usa para detectar duplicata
  - `usn = -1`, `mod` = epoch em segundos
- **`cards`** — uma linha por template gerado
  - Básico: 1 linha, `ord = 0`
  - **Cloze: uma linha por índice distinto**, `ord = indice - 1`. Errar isso faz o card sumir ou aparecer repetido.
  - Estado de card novo: `type=0, queue=0, due=<ordem>, ivl=0, factor=0, reps=0, lapses=0, left=0`

**Semente versionada.** Não reproduzir o schema e os JSONs de configuração padrão na mão. Gerar uma vez um `collection.anki2` vazio pelo próprio Anki, commitar como fixture, e a cada exportação: copiar a semente → abrir com `better-sqlite3` → sobrescrever `models` e `decks` no `col` → inserir `notes` e `cards` → zipar. Elimina a classe inteira de bugs de "coluna faltando" e "config default inválido".

### 5.3. IDs estáveis

`model_id` e `deck_id` são inteiros. Gerar uma vez, fixar como constante versionada, **nunca gerar em runtime**:

```ts
export const MODEL_ID_BASICO = 1607392319; // fixo, nunca mudar
export const MODEL_ID_CLOZE  = 1607392320; // fixo, nunca mudar
```

Se o `model_id` variar entre exportações, o Anki cria um note type novo a cada importação e o usuário acumula lixo na coleção.

`notes.id` e `cards.id` são timestamps em milissegundos e precisam ser únicos **dentro do arquivo**. Manter um contador que incrementa em caso de colisão — em Node, gerar 100 notas no mesmo tick é o caso comum, não a exceção.

### 5.4. GUID por card — a decisão central

O `genanki` derivava o GUID do hash dos campos por padrão, e a v1.0 desta RFC já apontava isso como armadilha: o usuário edita um card na tela de revisão, reexporta, e o Anki trata como nota **nova** — duplicata, exatamente o que o PRD proíbe.

Escrevendo o empacotador nós mesmos, isso deixa de ser uma armadilha a evitar e passa a ser uma decisão explícita: **o GUID é derivado do UUID do card no nosso banco**, estável através de edições.

```ts
const guid = base91(sha1(card.id).subarray(0, 8));
```

O Anki usa base91 para GUIDs próprios, mas aceita qualquer string estável e única. O que não pode é variar entre exportações do mesmo card.

Regenerar um card cria um `card.id` novo e, aí sim, uma nota nova — comportamento correto e intencional.

### 5.5. Note type de cloze

No JSON de `models`, o note type de cloze é `type: 1` (o básico é `type: 0`), com template contendo `{{cloze:Texto}}` na frente e no verso. Cloze exportado com note type básico é bug crítico: o Anki mostra as chaves literais na tela de revisão. Coberto por teste automatizado (§9).

### 5.6. Subdecks e tags

- Nome do baralho: derivado do nome do arquivo, sanitizado.
- Subdecks pela trilha de títulos, usando `::` (`Fisiologia::Cardiovascular::Ciclo cardíaco`), limitados a 3 níveis. Cada subdeck é uma entrada no JSON de `decks` com id próprio.
- Tags: `cardify::<slug-documento>::<slug-secao>`. Permite ao usuário filtrar e desfazer uma importação inteira.

### 5.7. Risco assumido

O `genanki` é mantido e testado contra mudanças do Anki por uma comunidade. **Nosso empacotador não é.** Quando o Anki mudar o formato, ninguém nos avisa — descobrimos por ticket de suporte.

Mitigações: fixar e monitorar as notas de versão do Anki; manter a suíte da §9 rodando contra o Anki mais recente em CI semanal; manter a opção B (sidecar Python) documentada como rota de fuga.

## 6. Modelo de dados

Schema Drizzle, tabelas em `snake_case`, campos TypeScript em `camelCase`.

```sql
users(id, email, created_at, ...)

subscriptions(id, user_id, plano, status, provider_sub_id,
              periodo_inicio, periodo_fim)

quota_periods(id, user_id, periodo_inicio, periodo_fim,
              limite_cards, cards_confirmados, cards_reservados)

documents(id, user_id, sha256, nome, paginas, bytes,
          storage_key, texto_extraido_key, expires_at)

jobs(id, user_id, document_id, status, params_hash,
     orcamento_centavos, custo_centavos, cards_gerados,
     idempotency_key, erro, created_at, started_at, finished_at)
-- status: pendente | ingerindo | gerando | empacotando | concluido
--       | parcial | falhou

chunks(id, job_id, ordem, trilha_titulos, texto, tokens)

cards(id UUID, job_id, chunk_id, tipo, frente, verso,
      texto_cloze, tags, fonte_offset, estado, ordem)
-- estado: gerado | editado | descartado

exports(id, job_id, formato, storage_key, bytes, expires_at)

llm_calls(id, job_id, estagio, modelo, tokens_in, tokens_out,
          custo_centavos, latencia_ms, created_at)
```

O `pg-boss` cria e gerencia o próprio schema (`pgboss.*`) — não misturar com as tabelas de domínio.

Índices relevantes: `documents(user_id, sha256)` para cache, `cards(job_id, ordem)` para a tela de revisão.

## 7. Fila, idempotência e cota

### 7.1. Fila: pg-boss

A v1.0 propunha `SELECT ... FOR UPDATE SKIP LOCKED` escrito à mão. Em Node existe o **pg-boss**, que é exatamente isso já resolvido: fila sobre Postgres com retry exponencial, agendamento, expiração, arquivamento e singleton keys.

```ts
await boss.send('gerar-baralho', { jobId }, {
  retryLimit: 3,
  retryBackoff: true,
  expireInMinutes: 20,
  singletonKey: idempotencyKey,   // dedup nativo
});
```

**Racional para continuar em Postgres e não ir para BullMQ/Redis:** o volume esperado é de dezenas de jobs por hora, não milhares por segundo. Postgres aguenta com folga e elimina um serviço, um ponto de falha e um custo fixo. O `singletonKey` do pg-boss ainda resolve parte da idempotência de graça.

Se o throughput um dia exigir, a troca para BullMQ é local — só o adaptador de fila muda, porque o worker não conhece o provedor (interface `FilaService` injetada).

Jobs travados são tratados pelo próprio `expireInMinutes` do pg-boss, que devolve o job para a fila. Manter o limite de 3 tentativas para não queimar orçamento de LLM em loop.

### 7.2. Idempotência

`idempotencyKey = sha256(userId + documentSha256 + paramsHash)`.

Requisição repetida com a mesma chave retorna o job existente em vez de criar outro. Protege contra duplo clique, retry de rede e refresh de página — cada um dos quais custaria dinheiro real em LLM. Implementado como guard/interceptor Nest lendo o header `Idempotency-Key`, com o `singletonKey` do pg-boss como segunda linha de defesa.

**Cache de documento:** se o mesmo usuário processar o mesmo SHA-256 com os mesmos parâmetros, reaproveitar os cards.

**Alternativa rejeitada: cache global entre usuários.** Seria a maior economia possível de custo — material de cursinho circula idêntico entre milhares de estudantes. Mas o PRD promete que o conteúdo do usuário não é reaproveitado, e um cache global significa que o card do usuário A é servido ao usuário B. Quebra a promessa de privacidade e cria exposição de direito autoral. Rejeitado por política, não por técnica.

### 7.3. Cota: reserva e confirmação

Contar cards no fim do job permite que dois jobs concorrentes estourem o plano. Padrão de duas fases:

1. **Reservar** na criação do job, dentro de uma transação com bloqueio de linha:

```ts
await db.transaction(async (tx) => {
  const [cota] = await tx.execute(sql`
    SELECT * FROM quota_periods
    WHERE user_id = ${userId} AND periodo_fim > now()
    FOR UPDATE
  `);
  if (cota.cardsConfirmados + cota.cardsReservados + estimativa > cota.limiteCards) {
    throw new PaymentRequiredException('cota_excedida');
  }
  // incrementa cards_reservados e cria o job na MESMA transação
});
```

2. **Confirmar** no fim: soma real vai para `cards_confirmados`, a reserva é liberada.
3. Job que falha ou expira libera a reserva integralmente.

O Drizzle foi escolhido justamente por não atrapalhar SQL desse tipo.

## 8. API

Todos os endpoints sob `/v1`, autenticação por sessão HttpOnly, exceto o fluxo anônimo.

| Método | Rota | Descrição |
|---|---|---|
| `POST` | `/uploads` | Devolve URL assinada + `documentId` |
| `POST` | `/jobs` | Cria job. Aceita `Idempotency-Key`. → `202` |
| `GET` | `/jobs/:id` | Estado e progresso |
| `GET` | `/jobs/:id/events` | SSE com progresso por estágio |
| `GET` | `/jobs/:id/cards` | Paginado, para a tela de revisão |
| `PATCH` | `/cards/:id` | Editar frente/verso/tipo |
| `DELETE` | `/cards/:id` | Marca como `descartado` |
| `POST` | `/cards/:id/regenerate` | Novo card, novo UUID |
| `POST` | `/exports` | `{jobId, formato}` → gera `.apkg`/CSV |
| `GET` | `/exports/:id/download` | Redirect para URL assinada, TTL 15 min |
| `POST` | `/webhooks/pagamento` | Assinatura verificada, processamento idempotente |

**SSE é nativo no Nest**, e essa é uma das vantagens concretas da mudança de stack:

```ts
@Sse('jobs/:id/events')
progresso(@Param('id') id: string): Observable<MessageEvent> {
  return this.jobsService.streamProgresso(id);
}
```

O worker publica progresso via `LISTEN/NOTIFY` do Postgres; a API converte em Observable. Sem broker adicional. Polling a cada 3s como fallback.

**Webhook de pagamento exige `rawBody`.** A verificação de assinatura roda sobre o corpo bruto, e o Nest/Fastify já fez o parse do JSON. Habilitar `rawBody: true` no bootstrap e registrar o parser cru só nessa rota — é o erro mais comum de integração de pagamento em Nest.

**Descarte é `soft delete`.** A taxa de descarte é a métrica de qualidade definida no PRD; apagar a linha destrói o dado que sustenta a melhoria do prompt.

### 8.1. Fluxo anônimo

O PRD exige entrega de valor antes do cadastro. Superfície de abuso óbvia — alguém pode rodar o endpoint em loop e queimar orçamento de LLM.

Controles:
- Sessão anônima com cookie assinado, TTL de 24h.
- Teto de 10 cards, 15 páginas e 5 MB por documento anônimo.
- Limite de 2 gerações por IP por dia (`@nestjs/throttler` com storage em Postgres ou memória por instância).
- Turnstile a partir da segunda geração.
- Teto global diário de gasto anônimo com desligamento automático e alerta.
- Ao cadastrar, o job anônimo é vinculado ao novo `userId` — o usuário não perde o trabalho.

## 9. Testes

Com o empacotador sendo nosso (§5), esta seção deixa de ser boa prática e vira **a rede de segurança do produto**.

O teste que mais importa não é unitário: é **importar o `.apkg` gerado em um Anki de verdade.**

Suíte de integração em CI, contra fixtures de PDF reais (aula de medicina, lei seca, slide exportado):

1. Gerar `.apkg`.
2. Abrir o zip, ler `collection.anki2` com `better-sqlite3`, conferir contagem de notas, `mid`, `guid`, `csum` e número de linhas em `cards`.
3. Reimportar o mesmo arquivo sobre a mesma coleção e afirmar que a contagem **não** aumentou.
4. Editar um card, reexportar, reimportar, afirmar que a nota foi atualizada e não duplicada.
5. Validar que toda nota cloze tem `mid == MODEL_ID_CLOZE`, que o campo casa com o regex de oclusão, e que **o número de linhas em `cards` é igual ao número de índices distintos de cloze**.
6. Rodar o Anki em modo headless (`anki --headless` via container Python no CI) para importar de fato e verificar ausência de erro.

O item 6 usa Python no CI. Isso é aceitável: é ferramenta de teste, não dependência de runtime em produção.

Complementar com verificação manual periódica no AnkiDroid, que tem comportamento de importação sutilmente diferente do desktop.

**Testes de ingestão:** fixtures de PDF com resultado esperado de agrupamento de linhas, já que o agrupamento agora é código nosso (§3.2) e não da biblioteca.

## 10. Observabilidade

Métricas por job: duração por estágio, tokens por estágio, custo, cards gerados, cards descartados na revisão, taxa de reparo de JSON, taxa de reprovação de cloze.

Painel mínimo:
- Custo de LLM por baralho (p50, p95) — vigia a margem do plano.
- Taxa de descarte na revisão — vigia a qualidade do prompt. Teto do PRD: 25%.
- Tempo até o primeiro card visível — vigia a ativação.
- Falhas de parsing por tipo de documento.

Instrumentação com `nestjs-pino` (log estruturado com correlação de request) e OpenTelemetry via `@opentelemetry/auto-instrumentations-node`.

Alertas: gasto diário acima do orçado, fila com profundidade crescente por mais de 10 min, taxa de falha de job acima de 5%.

## 11. Segurança e privacidade

- Uploads em bucket privado; todo acesso por URL assinada de curta duração.
- Retenção: PDF original apagado em 7 dias por regra de ciclo de vida; texto extraído em 30; `.apkg` em 30. Botão de exclusão imediata na conta.
- Conteúdo do usuário não é usado para treino e não vai para provedores sem cláusula de não-retenção. Verificar contratualmente antes de escolher o fornecedor de LLM.
- Worker de parsing isolado em processo próprio, sem credenciais de escrita (§3.1).
- Webhooks de pagamento com verificação de assinatura sobre `rawBody` e processamento idempotente por `eventId`.
- Auditoria de dependências no CI (`npm audit`, `socket.dev` ou equivalente). A árvore de dependências de um projeto Node é maior e mais rasa que a de um Python — a superfície de supply chain é maior e merece automação, não boa vontade.

**Injeção de prompt via documento.** O material subido é entrada não confiável que vai direto para o LLM; um PDF pode conter instruções embutidas. O impacto máximo é card ruim, já que a saída é validada contra schema zod, nunca executada e nunca alimenta chamada privilegiada. Aceitável, mas registrado — se um dia a saída do LLM passar a acionar ferramentas, isso vira problema sério.

## 12. Decisões abertas

1. **Fornecedor de LLM.** Cláusula de não-retenção, dois tiers de preço, latência aceitável no Brasil. Definir antes da F1.
2. **`pdfjs-dist` vs `mupdf` (WASM).** Se o agrupamento manual de linhas se mostrar frágil nos fixtures, migrar. Decidir na semana 1, com fixtures reais na mesa — não em teoria.
3. **Empacotador próprio vs sidecar Python.** Ponto de decisão ao fim da semana 3: se a suíte da §9 não estiver verde, cair para o `genanki` sem discussão. Não empurrar com a barriga.
4. **Limite de páginas do plano Ilimitado.** "Ilimitado" com teto real de 10.000 cards precisa de redação honesta nos termos.
5. **OCR (v1.1).** `tesseract.js` é WASM e bem mais lento que o binário nativo — medir contra PDF de cursinho escaneado antes de prometer no plano.
6. **Regenerar card mantém o GUID?** A proposta é não manter (novo card, novo GUID). Se o usuário regenerar muito, acumula duplicatas na reimportação. Contraproposta a discutir: manter o GUID e tratar como edição.
